2. Tradeoffs of the chosen path

Custom Next MDX (D1) vs a docs framework

Why this helps

  • Full control over routing, layout, and MDX component map
  • No framework upgrade churn (Fumadocs/Nextra APIs)
  • Easier to grow into a non-docs product surface later

What we take on

  • We must build sidebar, TOC, prev/next, and docs layout ourselves (extra P1 work)
  • Longer time-to-first-docs-page than Fumadocs/Nextra
  • Search (if wanted later) is fully custom

In-place cutover (D2)

Why this helps

  • Single repo/history; no dual-package forever
  • Content moves once into final locations

What we take on

  • Messy mid-migration tree until Docusaurus is deleted
  • Must use a branch so production Docusaurus stays safe

Exact URL parity (D3)

Why this helps

  • No SEO or shared-link breakage
  • Simpler acceptance: crawl old URL list as-is

What we take on

  • CamelCase slugs stay forever
  • Routing/file mapping must be case-sensitive and careful on macOS

Full blog keep (D4)

Why this helps

  • No broken /blog/* or feed consumers
  • Complete feature parity with current site

What we take on

  • Extra P2 work for tags/archive/RSS despite only 1 post today

Tailwind shell restyle (D5)

Why this helps

  • Removes Infima debt in one pass
  • One styling system with tutorials

What we take on

  • Homepage/nav/footer will not be pixel-identical to Docusaurus
  • Need a short visual QA pass, not a full redesign

Hosting deferred (D6)

Tradeoff accepted: we can build and validate locally (and on preview envs later) without choosing production host now. Risk: late discovery that the host is static-only may force output: 'export' adjustments. Mitigation: avoid hard dependencies on server-only features in P1 (no required search API route for v1).
