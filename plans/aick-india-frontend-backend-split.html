1. Verdict & feasibility

Feasible and justified. Today this repo is a static Docusaurus site (docs + marketing pages) with no server, auth, or database. Adding Google OAuth and Neon Postgres requires a backend (or equivalent serverless API). Separating that backend — first as a sibling directory, then as its own repo — matches how you plan to deploy and secure it.

The split is not needed for publishing docs alone. It becomes the right move once you need authenticated users, server-side secrets (OAuth client secret, DB URL), and an independently deployable API.

2. Why this approach (and why it’s better for your goal)

Matches the real need: deploy a backend

Static hosts (GitHub Pages, Netlify, Cloudflare Pages) are excellent for Docusaurus but cannot safely hold OAuth client secrets or talk to Postgres with privileged credentials. A small API service (Railway, Render, Fly.io, Cloud Run, Vercel serverless, etc.) needs its own build, env vars, and health checks. A dedicated backend package/repo keeps that deploy path clean.

Secrets & blast radius

Frontend env stays public (site URL, Google client ID). Backend env holds client secret, Neon connection string, session keys. Separate repos (or at least separate deploy units) reduce the chance of leaking secrets into a static build.

Independent release cadence

Docs/content can ship many times a day without redeploying the API. Auth/schema changes can ship without rebuilding the whole docs site.

Directory-first → repos-later is the pragmatic path

Starting with aick-india-frontend/ and aick-india-backend/ (monorepo or sibling folders) lets you wire CORS, shared types, and local Docker Compose before paying the cost of two remotes, two CI pipelines, and versioned contracts. Splitting remotes later is a mechanical move once the boundary is clear.

3. Trade-offs

Pros of separate backend

  • Independent deploy & scaling
  • Clear place for OAuth + DB
  • Backend stack can differ from Docusaurus
  • Easier to add future APIs (progress, fellowship forms, etc.)

Costs / cons

  • Two processes for local dev
  • CORS, cookies, and env coordination
  • Separate repos = harder cross-cutting PRs
  • Shared types need a package or duplication
  • More CI and ops surface area

Don’t split remotes on day one unless you must. Keep one repo with frontend/ and backend/ until auth + Neon work end-to-end. Then extract the backend repo for production deploy isolation.

Alternatives considered

Option Fit
Stay all-static + Auth0/Clerk hosted auth Faster auth, less control; still need somewhere for app data on Neon
Monorepo forever (FE + BE) Best DX; deploy can still target only backend/
Separate repos from day one Best isolation; slower early iteration

5. Google OAuth + Neon PostgreSQL

Why a backend is required for Google OAuth

The OAuth client secret and the code→token exchange must happen server-side. The frontend only starts the login and receives a session (httpOnly cookie preferred) or a short-lived access token after the backend completes the handshake with Google.

Minimal auth flow

  1. User clicks “Sign in with Google” on the frontend.
  2. Browser hits GET /auth/google on the backend → redirect to Google.
  3. Google redirects to /auth/google/callback with an auth code.
  4. Backend exchanges code for tokens, upserts user in Neon, sets session cookie.
  5. Frontend calls GET /me to know who’s logged in; logout clears session.

Neon as the database

  • Good fit: managed Postgres, serverless-friendly, branching for preview envs.
  • Start small: users (id, email, google_sub, name, avatar, created_at) and optionally sessions.
  • Access: use a pooled connection string from Neon; keep it only in backend env.

Interpreted intent: implement Google OAuth sign-on (not block it). If you meant something else (e.g. restrict to certain Google Workspace domains), add an allowlist check after token exchange.

6. Phased execution

1

Restructure in one repo

Move current site into frontend/. Scaffold backend/ with health check GET /health.

2

Neon + schema

Create Neon project, add migration for users, connect backend with env DATABASE_URL.

3

Google OAuth end-to-end

Google Cloud OAuth client (web), callback URL to backend, session cookies, CORS for frontend origin.

4

Frontend auth UI

Sign-in / sign-out on homepage or nav; call /me; gate any member-only pages if needed.

5

Deploy backend independently

Deploy API + env vars; keep frontend on static hosting pointing at API URL.

6

Optional: split into two GitHub repos

Extract backend/ history (or fresh repo), lock CORS to production frontend URL, document API contract.

8. Risks & open decisions

  • Cookie vs JWT: Prefer httpOnly cookies for a first-party web app; use JWT only if you need many clients.
  • Docusaurus + auth: Most docs stay public; auth is for members/fellowship/progress — don’t over-gate content early.
  • CORS + domains: Production frontend and API on related domains (e.g. aiseekhegaindia.org + api.…) simplifies cookies.
  • Google Cloud console: Separate OAuth clients for local vs production redirect URIs.
  • Astro leftovers: astro.config.mjs, index.astro, starter README — clean up when restructuring frontend.

Bottom line: Your plan is sound. Use a sibling backend/ directory first, wire Google OAuth + Neon, deploy the API alone, then promote to a separate repo when deploy isolation is the bottleneck — not before.
